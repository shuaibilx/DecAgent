# 游客文档浏览器走查记录

- 日期：2026-10-22（北京时间）
- 范围：游客本机体验指南、会话说明和权限/过期流程
- 测试入口：隔离 fixture `http://127.0.0.1:8025/`
- 模型/API 调用：无

## 环境隔离

- 使用仅绑定 `127.0.0.1` 的临时 Gateway、启用游客入口的 fixture 配置和一次性 PostgreSQL 数据库。
- 临时 PostgreSQL 使用独立容器 `decagent-guest-browser-20261022`，端口只映射到 `127.0.0.1`。
- 没有使用现有 `127.0.0.1:8000` 工作实例，没有开启公网或 Cloudflare Tunnel。
- fixture 未注册模拟业务插件；本走查只验证指南描述的会话和角色体验，没有提交工单或执行业务写入。

## 浏览器步骤与结果

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 开始体验 | 打开工作台 `/`，点“开始游客体验” | 创建隔离游客身份，进入业务工作台 |
| 恢复 | 刷新页面 | 同一浏览器恢复原游客和员工身份 |
| 切换角色 | 切换到 Chen Li（主管，Network） | 页面显示新角色，旧角色的身份数据清空 |
| 角色恢复 | 再次刷新 | 保留主管身份，不回退为旧角色 |
| 清空 | 点“清空游客空间”后刷新 | 返回登录入口，游客空间不能恢复 |
| 7 天过期 | 新建游客后，在隔离数据库将 `last_activity_at` 回拨到 8 天前并刷新 | 返回登录入口；`GET /api/v3/guest/session` 返回 401，旧身份不可恢复 |

清空及过期调用产生的两次 401 是预期的拒绝响应，因此过期场景浏览器控制台有两条预期错误记录；其余已启用游客流程没有控制台 warning/error。不会将这两条 401 描述成“全程控制台零错误”。

## 走查中修正的问题

临时启动器原先打印 `/business`，该地址返回 404；Gateway 的员工业务工作台实际位于 `/`。启动器现在统一使用 `WORKBENCH_PATH = "/"` 输出地址。回归测试 `evals/integration/test_business_guest_browser_fixture.py` 先因常量缺失失败，修正后通过：`1 passed`；针对该 fixture 的 Ruff 检查通过。

## 清理

停止 fixture 后，进程未执行到数据库清理代码；验收者随后核对临时容器内只剩该次创建的数据库，显式 `DROP DATABASE ... WITH (FORCE)` 删除并确认 `guest_browser_%` 数据库计数为 0，再停止带 `--rm` 的 PostgreSQL 容器。生产/本机工作实例数据未触及。

## 证据边界

此记录证明文档中的游客入口、角色切换、会话恢复、清空和过期路径已在隔离浏览器环境走查。它不证明游客业务任务、MCP 工具调用、Jev 建议质量、预算/队列实现或公开部署已经验收；其中 Jev 交互仍属于 OpenSpec 任务 2.5。

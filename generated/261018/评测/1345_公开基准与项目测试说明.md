# 公开基准与项目测试的区别

主要业务成绩来自已经选择的两个公开基准。项目自己写的测试用于验证执行代码、隔离边界和失败恢复；不能替代公开基准，也不能证明 Jev 比其他方案快。

| 层次 | 内容 | 能回答的问题 | 不能宣称 |
| --- | --- | --- | --- |
| 单元/契约回归 | 编译、参数绑定、分支、用量、错误处理 | 代码是否按契约运行 | 真实业务成功率 |
| 集成与核心链路 | PostgreSQL、MCP、工作台、恢复 | 组件是否真正连通且保持约束 | 全量公开 benchmark 已通过 |
| EnterpriseOps-Gym 主评 | CSM/ITSM，原任务和最终状态 verifier | 多步骤流程的端到端质量与效率 | 泛化到未测公司业务 |
| τ-Bench 补充评测 | retail/telecom 官方 test，原模拟用户/工具 | 对话、澄清、动态交互 | 真实员工速度或审批效果 |
| 自有合成样例 | 冻结 40/80 工作流集和记忆补充 | 定向回归、边界诊断 | 主成绩、生产阈值定策 |

~~~mermaid
flowchart LR
    C[项目代码改动] --> T[快速单元与契约回归]
    T --> I[真实数据库/MCP核心链路]
    I --> P[固定公开业务任务]
    P --> S[官方评分与公平配对]
    S --> R[质量/延迟/成本结论]
    A[自有合成样例] --> T
~~~

EnterpriseOps-Gym 的代码来自固定 GitHub 提交，任务数据来自固定 Hugging Face revision。τ-Bench 的代码、任务和官方划分来自固定 GitHub 提交。数据已缓存，无需用户手动再次下载；Git 不提交原始缓存。

环境已能响应工具不代表 Agent 完成了业务任务。所有正式成绩必须记录任务清单、精确分母、环境快照、模型实际版本、工具适配指纹、失败案例和未执行部分。同一个公开任务从相同初始状态分别执行三种策略；模拟用户费用单列，测试之间不学习。

本轮不会为了已有数据简化目标，也不会把正确分类、SELECT 1、脚本模拟或高 confidence 称为完整工作流成功。

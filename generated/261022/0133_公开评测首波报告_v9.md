# DecAgent v9 四域首波真实评测报告

## 结论

v9 首波在同一冻结 cohort 中实际执行了 4 个固定任务、8 条 ReAct/Plan 路线。8 条路线全部进入终态：2 条 failed、6 条 unknown、0 条 succeeded；8/8 环境清理均已核验。只有 ITSM/ReAct 与 τ telecom/ReAct 到达原始官方评分器，分数分别为 0.0，表示这两条尝试没有完成任务。其余 6 条没有官方分数。

因此，四域真实执行链被实际触发，但首波质量门槛没有通过；不能据此声称 Agent 已完成业务任务、ReAct/Plan 有效可比，或 Jev 带来收益。当前完整公开 benchmark 仍为 0/286 个有效完成任务，剩余 smoke 与全量评测暂停。

## 调用、Token 与费用完整性

本批共记录 14 次 Qwen 请求：primary 9 次（6 settled、3 unknown），τ user simulator 5 次（3 settled、2 unknown）；Jev 与裁判均为 0 次。9 次已结算请求报告了 72,390 个实际 Token，其中 primary 60,078、user simulator 12,312。5 次请求没有可用 usage，总计保留 252,296 个 Token 预留；其中 3 次 primary 在 60 秒处超时，2 次 user simulator worker 记录 ValueError。

按冻结的千问公开费率计算，已知 usage 的 profile 估算为 ¥0.0610926；5 次 unknown 的费用预留上界合计 ¥0.2796608；两者合计的冻结费率估算上界为 ¥0.3407534。这些数字是按冻结费率和 usage/reservation 计算的抵扣前估算，不是供应商账单，也不是现金实付。批次没有捕获逐请求 provider invoice、代金券抵扣或现金支付证据；不能因为用户账户有代金券就将费用记为零。

观察到 5/14（35.7%）请求 usage unknown。这个比例来自很小、固定且按角色/任务分层的工程首波，事件也不独立：两个 ValueError 都来自同一个 τ retail 任务，三个超时都来自 Plan 路线。因此它不能当作 Qwen 的一般故障概率；但这次观察足以说明当前路径还不能称为“偶发到可忽略”，更不能在未修复诊断前直接扩大批次。

还有 3 次工具 attempt：τ telecom 的两次只读工具调用 settled；CSM find_user 一次只读调用为 unknown。没有 Jev 请求。

批次墙钟为约 287.3 秒（4 分 47 秒），低于冻结的 4 小时停止线。没有达到资源上限；停止评测的原因是首波质量门槛未通过和异常诊断不足。已完成的 unknown 预留保留，不得自动释放或重发。

## 对 unknown 的离线诊断

- 三个 Plan primary timeout 均在约 60 秒后记为 unknown，且没有 provider request ID 或 usage。账本记录的输入上界分别为 51,653、60,124、62,435 Token，均低于冻结的 65,536 输入上限；另各预留 8,192 输出 Token，因此合计预留分别为 59,845、68,316、70,627。这些是估算上界，不是实际 Token。最后一个输入上界约为 profile 上限的 95.3%；接近上限不能证明大输入就是超时原因，也不能证明服务端是否收到请求。
- τ retail 两条 user simulator attempt 分别于北京时间 2026-10-22 01:22:34 和 01:22:44 进入 worker target ValueError，均没有 provider request ID 或 usage。v9 执行时，worker 把模型构造、工具绑定、HTTP 调用和响应处理期间未识别的异常统一为 target 阶段，因此现有记录无法判定 ValueError 发生于请求发出之前，还是发生于提供方已接收之后。
- 三个 Plan 超时发生于北京时间 01:20:11、01:21:27、01:23:47。它们同样缺少响应 usage/request ID。账本标记 dispatched 只说明本机已开始派发尝试，不证明请求一定到达服务商。
- CSM/ITSM 两个 EnterpriseOps 是 development_exposed；τ retail/telecom 使用 train，不涉及官方 test 80。用户确认没有在项目外查看 τ-Bench 官方 test 内容。

不得通过重放这些 attempts 来“补齐”诊断。若后续要对账，可按以上时间、模型和角色在千问兼容端点对应的服务商记录中查找；找不到匹配记录仍应保持账单 unknown。

## 后续工作顺序

1. 保持 v9 cohort、8 条路线和全部 5 个 Qwen unknown attempts 不变，不再从此账本派发请求。
2. 离线定位 worker ValueError 的可能来源，并改进安全诊断：区分模型客户端本地构造/参数错误、请求调用后未获可核验响应、收到响应但契约或 usage 不合格。只保存有限阶段、错误类别、HTTP 状态、请求 ID 和 usage；不记录 prompt、response body、工具参数、异常文本或凭证。先加回归测试再改实现。
3. 离线分析 Plan 请求的构造与尺寸上界，确认超时路径；不得在 v9 cohort 中调大 60 秒或重试。任何 profile、计划上下文或 timeout 改动都要产生可审阅的新候选/身份。
4. 对改动运行适用确定性、PostgreSQL、Ruff、wheel/MCP、Compose 和 OpenSpec strict 检查，并对最终候选 SHA 等待 GitHub CI 成功。
5. 完成诊断修复后，重新估算资源和 unknown 风险，形成新的 cohort/manifest、运行顺序及单独的派发授权。旧预算上限不是自动重试授权；不满足首波质量与官方评分门槛时不跑剩余 20 个 smoke、206+80 全量或 Jev 配对。
6. 真实评测受外部服务问题阻塞时，可继续游客隔离、预算队列和本机交付文档；它们与公开 benchmark 质量结论分开验收。

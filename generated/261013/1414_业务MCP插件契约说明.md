# service-tickets 2.0.0 MCP 插件契约

本文件记录 `mcp-business-runtime` 的契约阶段成果。当前已固定工具、输入输出 Schema 和打包 Skill 的内容摘要；员工认证、MCP HTTP 服务、批准与执行接入仍须按 OpenSpec 后续任务实现和验收。不能凭此文件认为业务 MCP 已可启动。

## 单一契约来源

| 来源 | 作用 |
| --- | --- |
| [manifest.json](../../decagent/business/tickets/manifest.json) | 十二项业务能力、参数与结果 Schema、效果、确认规则、工作流和 Jev 问题。 |
| [contracts.py](../../decagent/business/contracts.py) | 注册时校验 manifest，按同一份能力 Schema 生成规划工具并验证调用。 |
| [mcp_contract.py](../../decagent/business/mcp_contract.py) | 由能力 Schema 派生十四项 MCP wire 工具及操作结果 Schema，验证发现目录无漂移。 |
| [SKILL.md](../../decagent/business/tickets/SKILL.md) | 规划上下文；字节内容的 SHA-256 和描述与 manifest 绑定。 |

连接声明固定为 `service-tickets`、`streamable-http`、主协议 `2026-07-28` 与受信配置引用 `DECAGENT_TICKETS_MCP_URL`。manifest 不接受任意 endpoint 或命令入口。实际 URL 和员工凭据必须由可信运行配置解析，不能由模型参数决定。

## 工具表

| 类型 | MCP 工具 | 业务能力 |
| --- | --- | --- |
| 读 | `tickets_directory`, `tickets_get`, `tickets_list`, `tickets_receipt` | 同名人员/类别、工单、列表及已提交回执。 |
| 准备写 | `tickets_prepare_create`, `tickets_prepare_assign`, `tickets_prepare_start`, `tickets_prepare_close`, `tickets_prepare_reopen`, `tickets_prepare_comment`, `tickets_prepare_resolve`, `tickets_prepare_set_priority` | 八种业务写入只创建不可变操作；输入为 `request_id` 与该能力的 `params`。 |
| 操作 | `business_commit_operation`, `business_get_operation` | 用 `operation_id` 提交或查询现有操作。 |

四个读取工具的输入与结果直接使用对应业务 Schema。八个准备工具的 `params` 引用同一输入 Schema，操作成功结果里的 `result` 引用同一命令结果 Schema。提交与查询只接收 `operation_id`。每个工具的结果包络严格为成功 `{ok:true,data}` 或失败 `{ok:false,error:{code,message}}`；调用端应检查 `isError` 和结构化结果，兼容 text 只供旧客户端读取。

准备操作的状态只允许 `ready`、`awaiting_approval`、`running`、`unknown`、`succeeded`、`failed`、`rejected`、`expired`、`cancelled`。`succeeded` 必须携带与原命令 Schema 相符的结果。Skill 描述人如何选择参数与核实回执，不授予额外工具或业务权限；加载时重新校验文件内容和 manifest 摘要。

待确认入口使用同站相对地址 `/#operation=<id>`。客户端在当前工作台域名下打开它，不接受 MCP 响应给出的外部域名或脚本协议。非成功状态不携带业务结果或回执。

## 信任边界与恢复

业务参数中禁止 `requester_id`、`employee_id`、`principal`、`authorization`、token、grant、headers、URL/endpoint 等身份和传输字段。员工身份、创建者及 Agent 执行 grant 将由服务端从经过认证的上下文取得。工具目录的角色过滤只是减少可见工具；每次读写仍需服务端重新授权。MCP 注解不形成权限。

写入必须先准备，再由同一员工通过工作台确认需要批准的具体操作，随后用原 `operation_id` 提交。丢响应时先查询操作及回执；`unknown` 不是未提交的证明。`request_id` 与员工、命令和输入绑定，同键不同内容必须冲突。实际批准、事务提交和崩溃恢复由后续任务落地，不能直接用旧 CLI 回执代替。

独立 `mcp-cli 0.3.0` 只支持 `2025-11-25`，因此最终将用它验证兼容路径，并以 Python SDK 验证主协议。独立 Linux 主机验收保留待办。项目仍只操作本地模拟业务数据，不连接御龙或公司 API。

# DecAgent 外部用户自托管部署方案

**状态：** 方案稿，尚未作为生产部署实现
**更新时间：** 2026-10-17 17:06（北京时间）

## 目标与边界

目标是让运营方控制服务器、数据和模型密钥，同时让获授权的外部员工通过浏览器访问。首个可交付形态建议采用**每个客户组织一套独立实例、单台 Linux 主机、Docker Compose 部署**，避免首版承担共享 SaaS 的跨租户隔离复杂度。

这里的“外部用户”是互联网或企业网络外的员工访问服务，不表示开放匿名注册。若未来要求多个不相关客户共用一套数据库和服务，必须另行设计并验证 tenant ID、数据/密钥隔离、配额、备份和审计边界；当前方案不把共享多租户视为已支持能力。

## 当前项目与目标环境的差异

当前 Compose 将 PostgreSQL、API/Worker、executor-broker、egress proxy 和受限 runner 分离；API 的宿主端口绑定在 loopback，远程工作台 origin 要求 HTTPS。现有发布工作流由版本标签触发，在完整 CI 通过后发布 GHCR 镜像，再部署到本机 Windows Docker Desktop。

正式对外开放前还需补齐：

- owner 是单实例维护者身份；员工页面使用本地创建的模拟员工账号。邀请、找回、轮换、企业 SSO/MFA 和正式员工生命周期还没有形成生产级接入流程。
- 尚无独立 Linux 主机验收、Linux 部署脚本和异地备份恢复演练。
- 生产环境需要域名/TLS、防火墙、监控告警、升级回滚和容量验证；本机健康检查不能替代这些工作。
- 当前 GHCR 自托管 Runner 是本机部署工具，不等同于生产服务主机。公开仓库的自托管 Runner 不是干净隔离 VM，处理不可信工作流可能持续危及 Runner 和其可访问的秘密；生产 API 主机不应兼任 PR Runner。

## 推荐的单机生产拓扑

~~~mermaid
flowchart LR
    U[外部员工浏览器] -->|HTTPS 443| D[组织域名与 DNS]
    D --> F[路由器/主机防火墙]
    F -->|仅开放 80/443| RP[宿主机 Caddy 反向代理]
    RP -->|loopback HTTP| API[DecAgent API]
    API --> DB[(PostgreSQL 私有网络)]
    API --> W[业务 Worker]
    W --> B[executor-broker]
    B --> R[隔离 Runner]
    R --> EP[受限 egress proxy]
    W --> LLM[经批准的模型 API]
    EP --> MCP[已注册 MCP 服务]
    DB --> BK[加密异地备份]
    API --> OBS[健康、审计、告警]
~~~

建议 Caddy 作为宿主机服务运行，API 继续只监听 `127.0.0.1:8000`，避免代理进入数据库或 broker 网络。基础配置：

~~~caddyfile
agent.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8000
}
~~~

设置 `DECAGENT_PUBLIC_URL=https://agent.example.com`。反向代理头只信任本机 Caddy，不能让客户端伪造源 IP、协议或 Host。PostgreSQL、executor-broker、Docker socket、管理接口和内部 MCP 端口不得暴露公网；公网仅开放 80/443。SSH 走 VPN/管理网或受限密钥，禁用密码登录。

Caddy 可自动申请和续期 TLS 证书，前提是 DNS 指向主机、80/443 从互联网到达 Caddy，且证书数据目录持久化。若主机处于 CGNAT 或没有稳定公网入口，可用组织 VPN 或受控隧道；隧道会引入第三方网络依赖，需明确告知和评审。

## 身份、授权与组织隔离

1. **一组织一实例。** 每个客户组织独立数据库、数据卷和凭据，不在同一库中混放互不相关客户的数据。
2. **企业身份优先。** 优先接客户 OIDC/SAML；若首版用本地账号，需要管理员邀请、密码重置、强制停用、会话撤销、登录限速和 MFA 计划。关闭公共注册。
3. **owner 与员工分开。** owner 凭据只用于初始化/维护；普通员工仅访问自身任务、业务记忆和授权的 MCP 操作。管理入口优先置于 VPN 或单独管理域。
4. **预算与滥用控制。** 模型 Key 是实例级秘密；应按任务/员工记账，配置费用、速率和并发上限及异常告警。
5. **重新验证 ACL。** 测员工 A 无法访问员工 B 的任务、记忆、trace、凭据和业务资源；现有合成员工隔离测试不能自动证明所有新插件安全。
6. **数据最小化。** 明确保留期限、删除/导出流程、日志脱敏、模型供应商数据处理方式和用户告知。备份须加密异地保存并定期恢复演练。

## 主机与运行配置

- 使用专用、持续供电且受管理的 Linux x86_64 主机；操作系统、Docker Engine、Compose 插件按安全公告更新。先测真实负载，再决定并发量和规格。
- 使用可靠持久卷保存 PostgreSQL、控制数据与备份；设置磁盘告警、日志轮转、容器资源限制和重启策略。
- 用 Compose production overlay 与开发/本机配置分离；镜像固定到发布 digest，不用可变 `latest`。Docker 官方也建议使用独立生产 Compose 配置覆盖开发设置。
- 密钥放在受限权限的 secret 文件或秘密管理器；不写进镜像、Git、CI 日志或浏览器响应。
- 备份数据库和控制数据到加密异地存储，记录恢复目标并定期在隔离实例演练。迁移前备份，部署失败时保留恢复证据。
- 监控 API 健康、Worker 心跳/队列年龄、数据库连接与磁盘、Runner 失败、模型费用、TLS 续期和最近成功备份；日志只保留诊断必需字段并脱敏。

## 发布与回滚

首阶段采用**CI 验证的固定版本镜像 + 人工确认部署**，不追求无人值守生产更新：

~~~mermaid
sequenceDiagram
    participant Dev as 开发者
    participant CI as GitHub Actions CI
    participant GHCR as GHCR 镜像
    participant Admin as 自托管管理员
    participant Host as Linux Compose 主机
    Dev->>CI: PR / main 提交
    CI->>CI: Ruff、Python 矩阵、确定性与 PostgreSQL 集成测试
    CI->>CI: wheel/MCP/runner/Compose smoke
    Dev->>GHCR: 推送受 main 认可的版本标签
    GHCR->>CI: Release 复用完整 CI 作为门禁
    CI->>GHCR: 发布 control/executor/runner 镜像 digest
    Admin->>Host: 确认目标版本并运行部署
    Host->>Host: 备份、拉取 digest、迁移、健康检查
    alt 健康检查通过
        Host-->>Admin: 部署成功，保留备份与旧 digest
    else 检查失败
        Host-->>Admin: 停止升级并保留诊断/备份
        Admin->>Host: 按回退手册恢复旧镜像，必要时恢复数据库
    end
~~~

当前 `release.yml` 只实现 Windows 本机部署，不能直接当 Linux 生产交付。后续需单独实现 Linux 路径：确认目标实例和卷、备份数据库、拉取固定 digest、迁移、健康检查；失败时停止并保留恢复证据。首版接受短暂维护窗口、采用受控 recreate；只有明确有无停机要求后，再设计蓝绿发布和向后兼容迁移。

不要把公开 GitHub 仓库的普通 PR 流程接到持有生产 secret、Docker socket 或客户数据的常驻 Runner。首阶段由管理员执行受审查的部署命令。未来自动 CD 应使用受保护环境、人工审批、最小权限部署身份和隔离的部署执行器。

## 分阶段落地与准入条件

| 阶段 | 交付 | 进入下一阶段条件 |
| --- | --- | --- |
| 0. 生产准备 | OpenSpec 需求、身份方案、威胁边界、数据保留和可用性目标 | 明确一组织一实例、入口方式、维护责任人和恢复目标 |
| 1. Linux 隔离验收 | 新 Linux 主机、生产 Compose overlay、Caddy/TLS、备份恢复与升级回退 | 网络/权限检查通过；新装和恢复都通过；无真实客户数据 |
| 2. 内部试运行 | 邀请制、有限员工、真实插件只读与小额写入 | 员工隔离、审批、预算、审计、告警和人工回滚演练通过 |
| 3. 受控外部 Beta | 指定组织/用户、数据告知、限额和支持流程 | 真实业务 E2E、并发/恢复、备份、成本和安全验收通过 |
| 4. 稳定运营 | 定期发布、补丁、备份恢复演练、事件响应和容量复盘 | 按真实流量决定扩容或拆服务；不预先引入 Kubernetes |

### 对外开放前的 Go/No-Go 清单

- [ ] 管理员能管理员工账号生命周期；owner 运维入口不对普通员工开放。
- [ ] 未登录不能访问业务 API；HTTPS、CSRF、Cookie、安全头和登录限速通过浏览器验收。
- [ ] 员工间任务、记忆、MCP 凭据和 trace 隔离通过集成与 E2E 测试。
- [ ] 只有获批插件可执行；关键写操作保留员工确认与结果核实。
- [ ] API、PostgreSQL、broker、runner 控制面和 Docker socket 无公网监听。
- [ ] 固定镜像 digest；secret 不进日志/响应；模型和执行预算能限制滥用成本。
- [ ] 异地备份恢复演练成功；升级失败能回到已知版本并保留恢复证据。
- [ ] 至少覆盖登录、建任务、动态分支、MCP 查询/写入、人工等待/恢复和最终回执的端到端验收。
- [ ] 已明确维护人员、告警渠道、漏洞修复时限、数据删除/导出和故障沟通流程。

## 推荐结论

先交付“**每个组织独立部署、邀请制员工访问的单机自托管服务**”，暂不做一个实例服务多个陌生客户的 SaaS 多租户。当前 Windows Docker Desktop 与自托管 Runner 适合开发和本机发布验证；正式对外服务前，优先完成员工身份管理、Linux 部署/恢复验收、外网入口与安全边界、真实业务 E2E 和运营预案。

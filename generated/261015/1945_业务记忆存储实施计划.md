# 业务记忆存储实施计划

对应已批准 OpenSpec `jev-conditional-workflows` 6.3 和 design 第 7 节。
目标：持久保存有真实来源的员工偏好和流程经验，先过滤员工与版本，再提供有限候选。

## 文件边界

- `decagent/business/memory.py`：`MemoryContext`、`BusinessMemoryStore`，身份重验、来源校验、确认、去重、版本/期限过滤与撤销。
- `decagent/storage/016_business_memory.sql`：独立业务记忆、来源撤销、提炼规则及不可变审计；不改仓库修复记忆。
- `evals/integration/test_business_memory.py`：独立数据库验证全部持久行为。
- `evals/deterministic/test_business_memory_contracts.py`：边界、内容类型、指纹输入校验。
- `database.py` 的迁移登记由根代理负责，避免共享文件冲突。

## 实施顺序

1. 写失败测试：偏好待确认、本人浏览器确认、当前身份、重复去重与 30 天期限。
2. 写失败测试：同公司不同员工隔离、scope/account/contract/question/plan 版本漂移及过期排除。
3. 写失败测试：真实同员工来源校验、来源撤销、当前业务事实和授权内容不能成为长期事实。
4. 写失败测试：流程经验要求真实成功回执及已发布固定提炼规则、默认 7 天、缺规则不激活。
5. 观察 RED，增加 016 迁移和最小服务实现，再运行 GREEN。
6. 验证撤销和 supersedes 保留历史；审计引用不包含认证 token 或原始秘密。
7. 运行目标 ruff 和业务记忆集成回归，生成实际 API 与验证记录。

## 约束

- 所有 integration case 派生新 `case_*` 数据库。
- 测试连接仅从私文件读取，使用已约定 `PGOPTIONS`，不打印连接 URL。
- 不访问付费模型、live 或用户数据库；不修改 OpenSpec checkbox。
- 不接 gateway，后续 6.4/6.5 可复用服务接口。

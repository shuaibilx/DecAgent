# Jev 条件计划改造计划与探索结论

生成时间：2026-10-15 05:17，北京时间。本次交付是需求分析、实施路线和 OpenSpec change，不表示新运行机制已经实施。

## 项目要证明什么

DecAgent 的特点是：少量通用 LLM 编排可验证的条件计划，Jev 处理可信边界内的语义判断，代码和 MCP 执行业务；遇到低确定性时请人决定，遇到计划失效时才受控重规划。

首阶段只覆盖已注册 MCP 工具和 Skill 的模拟公司业务。御龙仓库是接入方式的参考，不能作为可用后端。现有员工身份、权限、写入确认与回执机制继续承载执行。Pi 保留为可替换规划器的候选实现。

## 已确认的决策

| 项目 | 本轮约定 |
| --- | --- |
| 正常规划开销 | 目标 1–3 次实际通用模型请求；异常可受控追加；重试、摘要、最终回复均计数 |
| 分支 | 预规划已知分支，参数引用未来真实结果；仅异常局部重规划 |
| 判断契约 | 主模型组合已发布模板；不能临时改变问题语义、选项来源、尺度或权限 |
| 计划复用 | 已验证且当前适用的计划可零通用 LLM；动态事实和权限仍重新读取 |
| 人工接管 | 当前分支关键判断低于阈值直接暂停，不因此自动追加通用 LLM |
| 记忆 | 持久任务状态 + 员工隔离的有限偏好和流程经验；业务事实不靠旧记忆推定 |
| 质量目标 | 自动处理部分实测正确率至少 95%，同时报告样本量和 95% 统计置信区间 |
| 阈值选择 | 在验证集达到质量目标的候选中最大化覆盖；冻结后测试，不通过就如实报告 |
| 评测 | 公开语义数据 + 独立模拟流程；真实模型、理想人工和实际人工分别报告 |
| 部署 | 本轮不实施部署；保留独立 Linux 验收待办 |

质量目标是点估计要求，不等于“统计置信区间下界必须达到 95%”，也不等于将 Jev 阈值写为 0.95。报告必须分别展示这三个量；样本不足时不得宣称已建立可靠默认值。

## 探索发现与改造范围

| 已核实的现状 | 本轮设计方向 |
| --- | --- |
| business/services.py 接收普通工具队列；队列耗尽可再次调用 primary | 新增有类型的条件计划和解释器，新任务不再以队列耗尽作为调用模型的理由 |
| questions.py 已按契约构造 Choice/Noul/Score | 保留可信语义，增加模板版本、输入绑定和执行次序 |
| checkpoint 为 business-2，保存消息、队列和观察 | 新版本保存计划版本、节点、等待原因、决策和参数来源；旧任务保留专用恢复兼容 |
| decision_records 有判断记录，但不自动进入后续规划上下文 | 建立结构化投影，挑选与当前重规划有关的决策、观察、回执与人工更正 |
| storage/usage.py 按混合模型记录计数，工具 guard 也检查模型次数 | 分开 primary/Jev 额度与执行额度；主模型额度耗尽不阻止已有计划在其他预算内推进 |
| 原 memory 契约针对项目、Git SHA 和 PR 合并 | 新增业务记忆契约，复用证据与撤销思想；保留历史修复模块 |
| MCP prepare/确认/commit、幂等回执、员工身份已实现 | 复用这些边界；重规划、记忆、人工选项均不能绕过它们 |

实现代码和权威 OpenSpec 均位于 DecAgent 根目录；规格保存在 openspec/。不另建第二个 OpenSpec 根，也不把源码放进 generated/。

## 六阶段实施路线

| 阶段 | 主要交付 | 阶段验收 |
| --- | --- | --- |
| 1. 计划契约与规划器 | 计划 schema、可信模板注册表、编译校验、可替换规划器；合法引用、条件边、合流和有界重试 | 非法工具、权限指令、悬空引用、无界循环、不可达完成条件不能进入执行 |
| 2. 持久执行与预算 | 新图版本、节点日志、原节点恢复、未来参数绑定、局部重规划、分离模型额度 | 已知分支不调用主模型；重启不重复写入；未知提交仍以原操作 ID 核实 |
| 3. 确定性与人工接管 | 分类型阈值策略、持久待办、原员工响应、合法候选和证据、恢复校验 | 低分直接等人；未走分支不打断；高分不跳过敏感写入确认 |
| 4. 上下文与记忆 | 工作记忆、受限上下文投影、证据化跨任务记忆、纠错撤销和过期 | 外部 Jev 记录可供下次规划使用；无跨员工泄漏；无隐藏摘要调用 |
| 5. 已验证计划复用 | 发布与失效、适用条件、版本依赖、真实数据重绑定 | 冷启动首次编排与热复用分别统计；适用复用流程实际 primary 请求为零 |
| 6. 评测与交付 | 数据清单、冻结划分、配对基线、阈值曲线、工作台 trace、指南与各种图 | 安全与恢复检查通过；真实性能按质量、覆盖、请求数、成本、延迟报告 |

阶段 1 → 2 → 3 为主线。阶段 4、5 在持久执行稳定后开展；阶段 6 的数据契约和基线留存必须从阶段 1 开始，最终评测在所有功能冻结后完成。

## 关键设计判断

首次规划负责表达已知路径，不预测尚未出现的工单 ID、候选人员或工具结果。计划中的引用由代码在执行前解析；缺少字段时进入补充信息路径。自由文本生成确有需要才使用主模型，并计入实际请求数。

批量 Jev 只合并输入状态一致且问题互不依赖的节点；需要前序答案或新工具结果的判断必须后移。未消费答案可以保留审计，但不能提前触发人工待办。

Choice/Score 使用服务返回的 confidence；Noul 使用 yes 概率，适配层可计算 abs(2p-1)。前者是答案分布集中程度，后者是归一化距离，都需要本业务验证后才能作为自动推进条件。[TypeSafe 定义](https://docs.typesafe.ai/confidence)

已执行副作用、待审批操作和未知结果构成重规划边界。局部计划只能修改未执行部分；不能用新操作 ID 重试未知提交。人工改选同样要重新核对候选、权限和资源版本。

## 评测计划

1. 优先接入 [Kaggle Bitext 发布者数据](https://www.kaggle.com/datasets/bitext/training-dataset-for-chatbotsvirtual-assistants/metadata)，获取时固定下载版本、哈希与许可；未确认前不打包原始数据。使用 [CLINC150 原作者数据](https://github.com/clinc/oos-eval) 另外测范围外识别，保留其官方划分。两者只证明语义判断能力。
2. 固定中文模拟业务场景，覆盖分支、动态参数、未知提交、权限变化、人工改选、重启和记忆隔离。数据标签不暴露给待测 Agent。
3. 语义层比较同输入的主模型和 Jev，离线扫描 0、0.50、0.70、0.80、0.90、0.95、0.99。流程层比较同一主模型逐步规划、既有 MCP 路线和新条件计划，并区分冷启动与热复用。
4. 默认策略在验证集选择；正式测试冻结模型解析版本、模板、策略、计划和数据清单。自动样本为零或不足时不生成有效默认策略。每个决策族分别核查，不能用总体平均掩盖某个族的错误。
5. 发布覆盖率—错误率、阈值—人工负担、成本/延迟对比图。人工模拟与真实等待分开；敏感写入确认与语义不确定性接管分开。
6. Jev 仍受此前累计 1 美元授权约束，读取既有账本后分批执行；千问免费额度不免除请求和 token 计数。费用未知继续采用原有约束。本次规划不调用付费模型。

性能“通过”需要质量和安全先通过，再证明相同测试条件下减少主模型调用、成本和延迟。若只有部分场景改善，要报告适用范围，不预先承诺倍数。

# 条件计划执行与恢复

本说明对应 `jev-conditional-workflows` 第 3 组。当前默认入口仍为 business-2；源码支持按开关创建 business-3，并按任务原版本恢复。源码 schema 17，用户业务库尚未迁移。完整工作台、真实质量和性能验收仍在实施。

## 节点身份与冻结区

计划是有限 JSON 数据：至多 32 个节点、分支深度 4、修订至多 4；支持 read_tool、governed_write、transform、decide、branch、join、ask_user、complete。解释器只沿已保存的实际控制边推进，未走分支不产生业务动作。

~~~mermaid
stateDiagram-v2
  [*] --> Running: 节点定义与输入摘要持久化
  Running --> Waiting: 原员工回复或明确恢复
  Running --> Unknown: 远端结果尚不能核实
  Running --> Succeeded: 保存真实结果及控制边
  Running --> Failed: 已知错误，按声明的退出边
  Waiting --> Running: 原绑定仍有效的受控恢复
  Waiting --> Skipped: 有效补充使未决推断退出，申请有限补丁
  Unknown --> Unknown: 继续核实原操作
  Unknown --> Succeeded: 核实原操作回执
  Succeeded --> [*]
  Failed --> [*]
  Skipped --> [*]
~~~

节点以 task、node ID、generation、定义摘要和输入摘要绑定。已执行、等待、未知、失败、跳过、已准备或已分派的前缀不能由主模型删除。次数与控制步数在重启后累计；不能用新的节点名重复已提交操作。

原员工编辑待确认参数时，先证明旧服务端操作已拒绝、原 action 已 denied，再发布新 revision 和同节点的新 generation。旧节点、审批和 operation ID 保留；新具体参数需要新确认。结果未知的操作不允许用此路径覆盖。

## 模型请求的三个崩溃边界

~~~mermaid
sequenceDiagram
  participant H as 规划协调器
  participant DB as 持久日志
  participant L as 用量账本
  participant M as 主模型
  H->>DB: 核对当前上下文 epoch、父版本并保存请求 intent
  H->>L: 原子预留实际请求额度
  L->>DB: 实际发送前复验 epoch、租约、取消及预算
  alt 发送前已失效
    L->>DB: not_sent，释放未发送预留
  else 当前允许发送
    L->>M: 规划或唯一一次格式修复
    M-->>L: 响应及实际 usage
    L->>DB: 结算 responded 或保留 unknown
    H->>DB: 保存校验后的安全 proposal
    H->>DB: 同事务检查当前 epoch、父版本、冻结区并发布
  end
~~~

| 退出位置 | 恢复行为 |
| --- | --- |
| intent 之前 | 没有已发送证据；重新构建当前授权上下文。 |
| intent 之后，安全 proposal 尚未保存 | 保留原请求身份和未知约束，进入核实；不因事件序号、预算或租约改变自动重发。 |
| 安全 proposal 已保存，plan 尚未发布 | 校验来源边界和内容摘要后复用该 proposal，不再次调用模型。 |
| plan 已发布，checkpoint 尚未推进 | 使用原 plan 和已持久节点事实；不重新规划。 |

请求的逻辑键绑定任务、目标修订、父摘要和用途；发送状态、实际请求数和费用由共享 UsageLedger 保存。格式修复是另一笔真实请求，也执行同样的发送前检查。Jev 的批次请求和每题消费分别记录。

权限版本在构造上下文后、预留后、响应后或发布前改变，都不能将旧上下文重新标成当前事实。已发送或响应无效的请求仍计费；未知费用不能猜成零。当前核实等待不会自动授权另一次模型尝试。

## 提交响应丢失

~~~mermaid
sequenceDiagram
  participant R as 条件解释器
  participant A as action日志
  participant S as MCP服务
  participant B as 业务事务
  R->>A: 保存稳定逻辑键与请求参数
  R->>S: prepare 原 request key
  S-->>R: 原 operation ID
  R->>A: 绑定原 operation ID
  R->>S: commit
  S->>B: 工单、历史、回执同事务提交
  B-->>S: 已提交
  S--xR: 响应丢失或进程退出
  R->>A: 保留 unknown，不生成替代操作
  Note over R,A: 新 worker 使用原任务及原 generation 事实恢复
  R->>S: 查询原 operation ID
  S-->>R: 原回执、输入绑定与资源版本
  R->>A: 验证回执并保存节点结果
~~~

有回执不等于当前业务事实仍未变化；后续任务需要最新数据时仍通过 MCP 读取。尚不能核实的结果继续等待，不将模型“完成了”的文字当作成功。

## 数据失效与恢复

员工、scope 和 account revision 来自当前数据库。旧读结果、旧候选或旧澄清在 epoch 变化后只保留引用与摘要，不能再次进入规划或 Jev 判断。普通 ask_user 和范围澄清都绑定原员工、节点定义、generation、输入摘要及权限版本。

已有节点的来源失效时，保留原输入和原操作，返回明确 reconciliation；旧审批只作为 original_approval_id 审计引用，不能被新的 reconciliation 当成当前审批消费。范围澄清的新回复可以触发受限补丁；补丁必须安排新的当前授权读取，不能给旧目录更换版本标签。

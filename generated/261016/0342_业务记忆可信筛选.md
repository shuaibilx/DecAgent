# 业务记忆写入提议可信筛选（OpenSpec 6.4）

实现位置：`decagent/business/memory_write_evaluator.py`。Jev 只使用固定 `memory_write` 模板评估有证据的写入提议，不负责选择任务上下文中的记忆，不直接保存或激活记忆。

## 读取边界

通用规划不搜索或自动注入跨任务记忆。读取只能由已发布工作流中的 `verified_memory` 绑定触发，绑定使用稳定 `memory_kind + subject` 槽，不含员工记录 ID：

```json
{"source":"verified_memory","memory_kind":"confirmed_preference","subject":"response_language","path":["value"]}
```

运行时按当前认证员工精确解析唯一有效槽，重新检查公司/业务范围、scope/account revision、TTL、证据来源与契约/问题/计划指纹。槽缺失、失效或歧义时暂停依赖节点；不回退到候选搜索，也不向 Jev 或通用规划器发送读取判断请求。写入筛选请求中出现的现有记忆只用于核查冲突，不会被当作当前任务记忆注入。

## 写入提议

`BusinessMemoryWriteEvaluator.evaluate_preference` 仅接收注册偏好 subject、有限 value、本人真实证据引用与可选 supersedes；`evaluate_experience` 仅接收已发布经验规则版本和同员工真实成功回执。候选来源、当前身份与 task 由可信运行时提供，调用方不能传入任意候选正文。

未知问题模板、伪造来源、缺失规则、无效回执和不支持的偏好 subject 在发起 Jev 请求前拒绝。同一证据、内容、槽和版本上下文已经存在时直接返回 `duplicate`，不重复调用模型、不延长 TTL。

策略必须显式绑定 `(policy_id, policy_version)`。组件从 `DecisionPolicyStore` 读取当前已发布策略，核对真实模型版本、适用范围与原始答案。该决策只代表是否保留提议，不代表持久化批准。

示意调用中的身份、上下文、证据和策略须来自当前运行时，不能来自员工提交的请求正文：

```python
from decagent.business.memory_write_evaluator import BusinessMemoryWriteEvaluator

writer = BusinessMemoryWriteEvaluator(
    database,
    api_key=settings.jev_api_key,
    model=settings.jev_model,
    provider=settings.jev_provider,
    reservation_usd=config.jev_reservation,
    dataset_version=published_dataset_version,
    before_dispatch=worker_guard,
)
proposal = writer.evaluate_preference(
    identity,
    current_memory_context,
    task_id=task_id,
    subject="response_language",
    value="中文",
    evidence_refs=[verified_source_ref],
    policy=(write_policy_id, write_policy_version),
)
```

`retained` 仅表示 Jev 在当前可信证据下建议保留提议。调用方仍须调用 store 的证据校验；偏好进入 `pending_confirmation` 后，由原员工确认精确 digest，经验仍须匹配已发布规则和真实回执。`manual`、`discarded`、模型错误或证据变化都不会写入记忆。所有结果的 `primary_fallback` 和 `grants_write_authority` 都为 false。

`retained` 返回 `requires_store_validation=True`，调用方仍须：

1. 对偏好调用 `BusinessMemoryStore.propose_preference`，得到 pending_confirmation；经原员工浏览器确认后调用 `confirm_preference`。
2. 对经验调用 `record_experience`，重新检查当前已发布提炼规则、真实成功回执、权限与去重。

不能把 Jev 的 retain 当成本人确认、回执验证或活动记忆。`discarded` 不写业务记忆，低分和 review 返回 `manual`。并发新增的重复项最终仍由 store 的去重约束处理。

## 请求额度与新鲜度

所有模型请求使用已有 `DecisionRequest`、`JevAdapter` 和绑定当前 task 的 `LedgerAttemptBudget(UsageLedger(...))`。每次 HTTP attempt，包括提供方重试，分别预留并结算到共享账本。首次用途为 `memory_write_screening`，重试用途为 `provider_retry`；主模型与 Jev 额度不另开账本。未知费用会阻止继续请求；没有可验证提议时在发请求前失败。

每次发送前和返回后都重新查询真实写入来源及当前策略。来源撤销、候选冲突变化、凭据失效和策略变化会阻止消费原答案。调用方提供的 `before_dispatch` 应继续检查当前 worker 的租约与取消边界。工作流槽读取则由执行器在每个依赖节点分派前独立解析与复核，不经此 Jev 写入筛选器。

## 验证方式与限制

集成测试使用 `evals/integration/conftest.py` 创建独立 `case_*` PostgreSQL 数据库，私有数据库地址只读入环境变量，不打印。HTTP 经 `httpx.MockTransport` 注入到真实 `JevAdapter`；没有发送付费模型请求。测试证明工程边界与预算记账，不证明真实 Jev 语义质量，也没有发布正式评测阈值。

```powershell
$env:DECAGENT_TEST_DATABASE_URL = (Get-Content -LiteralPath '.decagent/conditional-tests/database-url' -Raw).Trim()
$env:PGOPTIONS = '-c max_parallel_workers_per_gather=0 -c jit=off -c lock_timeout=15000'
& '.venv/Scripts/python.exe' -m pytest evals/integration/test_business_memory_write_evaluator.py -q --tb=short
& '.venv/Scripts/python.exe' -m pytest evals/integration/test_optional_memory_interventions.py -q --tb=short
& '.venv/Scripts/python.exe' -m pytest evals/deterministic/test_business_decision_policy.py evals/deterministic/test_business_policy_reports.py -q --tb=short
& '.venv/Scripts/python.exe' -m ruff check decagent/business/memory_write_evaluator.py evals/integration/test_business_memory_write_evaluator.py
```

写入筛选组件不修改 SQL 016 或 live 配置。稳定槽绑定 schema、已发布工作流限定和节点前复核由 business-3 计划运行时实施。

历史验证记录：旧版候选语义筛选 24 passed（163.12s），可选记忆规则集成测试 4 passed（9.71s），判决门控/策略报告确定性测试 101 passed（2.20s）。当前契约移除了业务记忆通用 Jev 读取选择路径；当前写入筛选和稳定槽回归以本轮测试记录为准。旧语义读取用例已由稳定槽解析测试替代。

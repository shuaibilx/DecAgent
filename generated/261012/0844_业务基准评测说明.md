# 本地业务基准评测操作说明

生成时间：2026-10-12 08:44（北京时间）。

本交付对应 OpenSpec 6.1。初稿只验证评测工具；后续真实探测、开发校准和完整验收的结果单独记录，不能用本文作为真实模型提效证明。代码和命令均在同级 DecAgent 项目中运行。

当前已有[完整 720 次实测](2341_业务固定集完整实测.md)，严格结果 not_passed：7 个 hybrid trial 用量不完整，六类 Jev 判断全部禁用。该报告绑定完成判定与拒绝记账修复前版本。[现版本功能验证](../261013/0158_现版本修复与功能验证.md)另行记录修复后回归与 9 次独立探测，不重算、拼接或替代固定对照，也不构成 Jev 收益证明。

## 冻结数据与比较条件

固定数据为 `evals/benchmarks/business/frozen-v1.json`，版本 `business-synthetic-reference-v1`，schema `business-evaluation-dataset-1`。SHA-256 为：

`6b21910ff04dc995d878e7c8e62f570ee0d484febc3f5ce718b15eb22cf5fa92`

数据在任何现场调用前冻结。120 条模板合成案例分为 40 条开发集（24 常见、8 复杂、8 边界）和 80 条固定验收集（48 常见、16 复杂、16 边界）。所有标签明确为 `synthetic-reference`，没有独立人工标注或真实企业效果证据。合成案例覆盖目录、创建优先级、分派、开始、解决、关闭、重开、评论、优先级变更、查询、复合任务、重名、非法关闭、缺失解决记录和否定写入；模板重复和范围有限意味着结果不能外推到任意企业业务。

加载器检查 schema、固定版本、标签来源、唯一 ID、分组数量、自身 checksum 和已冻结 checksum。重算 checksum 不能在同一版本下改写案例；生成命令也拒绝覆盖现存数据文件。新业务或标签变化应创建新的数据版本并重新开发校准，不能修改验收集后继续使用原 profile。

三策略都调用实际的 `BusinessServices`、`BusinessWorker`、`CliRunner`，使用同一增强清单、Skill、目录和执行治理。每个 trial 从相同初始工单状态重新创建资源；新 UUID 是隔离手段。参考标签仅进入评分器和开发拟合，不交给规划器，也不会覆写规则策略结果。规则无法完成的自然语言或复合请求保留澄清/失败，仍进入分母。

默认验收有 720 个 trial：80 案例 × 3 策略 × 3 轮。同一个案例的 rule/main/hybrid 相邻交错，每轮旋转策略位置及案例起点。客户端 Jev cache_ttl=0、retries=0，每个 trial 使用新的任务 ID，不复用前一 trial 的决策记录。没有声称关闭操作系统、PostgreSQL 或模型服务内部缓存。

## 离线命令

以下命令从 DecAgent 项目根目录执行，不访问模型服务：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business inspect
.venv/Scripts/python.exe -m decagent.evaluation.business generate --output .decagent/business-eval/frozen-copy.json
.venv/Scripts/python.exe -m pytest evals/deterministic/test_business_evaluation.py -q
.venv/Scripts/python.exe -m ruff check decagent/evaluation/business evals/deterministic/test_business_evaluation.py evals/integration/test_business_evaluation.py
```

不带子命令也默认执行 inspect。generate 创建相同冻结数据的新副本，目标存在时拒绝覆盖。`--dataset` 是全局参数，必须放在子命令前。

PostgreSQL 集成测试使用 `DECAGENT_TEST_DATABASE_URL` 作为创建数据库的来源：

```powershell
.venv/Scripts/python.exe -m pytest evals/integration/test_business_evaluation.py -q
```

测试在来源服务器上另建 `businessbench_<uuid>` 专用库，迁移一次并在同一库内串行执行测试。不会重置、删除或运行任务到来源库；没有配置变量时明确 skip。新评测库保留证据，不自动 drop。仅在经名称验证的专用库内清理业务工单、历史和业务回执；app 任务、决策、动作、usage 和 checkpoint 保留。后续 trial 不应恢复已经评分结束的旧任务。

## 累计 Jev 预算

所有探测、开发采集和验收必须使用同一个持久化账本路径：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business ledger-init --ledger .decagent/business-eval/global-jev-ledger.json
```

初始化只允许新文件。账本固定记入已有累计费用 $0.000253176，累计上限 $1，初始剩余 $0.999746824。每次 HTTP 调用前同时预留全局账本和任务账本；已知 usage 结算，未知 usage 或未完成预留阻止后续 Jev 调用。实际费用超过预留会保留账本并停止。文件锁竞争、丢失或格式错误也不会按零费用继续。中断后的 pending/unknown 记录必须核查，不能删除账本或重新初始化来重置历史消费。

TypeSafe 响应未返回费用且未配置费用估算时，费用保持未知并停止。可使用已经核实的版本化每百万 token 单价，向 live 命令同时传 `--jev-price-version`、`--jev-input-per-million` 和 `--jev-output-per-million`；不能仅填一个费率。价格版本及成本来源写入账本归因和报告。这份指南没有指定或声称某个当前价目。

千问沿用用户已经授权的免费额度和版本化价格设置；正常主模型调用仍保留 tokens 和 calls。只有缺少已知价格且需要免费额度路径时，才使用 `--main-free-quota`，同时配置 `DECAGENT_MAIN_UNKNOWN_RESERVATION` 和有限任务预算；该选项仅明确忽略主模型的价格未知，不能忽略 tokens 缺失、Jev 未知费用或预算暂停。没有免费额度授权时不能用未知费用当作零。

## 现场采集与拟合：只用开发集

现场命令都需要显式 `--live`、已初始化全局账本、来源测试数据库和全新输出路径。读取既有环境模型配置；没有密钥时在请求前报错。请先确认 `DECAGENT_TEST_DATABASE_URL` 指向专门测试服务器。命令中的来源 DSN 仅用于创建新库，不作为任务运行库。

先做一条有界采集，核对实际模型、usage、费用和保存文件：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business calibrate-collect --live --ledger .decagent/business-eval/global-jev-ledger.json --source-database "$env:DECAGENT_TEST_DATABASE_URL" --max-cases 1 --output .decagent/business-eval/dev-probe.json
```

探测导出明确 incomplete，不能用于拟合。确认探测正常并有预算后，采集固定 40 开发案例：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business calibrate-collect --live --ledger .decagent/business-eval/global-jev-ledger.json --source-database "$env:DECAGENT_TEST_DATABASE_URL" --output .decagent/business-eval/development.json
.venv/Scripts/python.exe -m decagent.evaluation.business calibrate-fit --input .decagent/business-eval/development.json --output .decagent/business-eval/profile.json
```

采集通过实际 CLI 准备目录和工单，并记录每条请求自己的 evidence、context、实际模型、完整 typed answers 和 attempts。采集任务只收集判断，结束后标记 cancelled，并明确 business_goal_executed=false；不伪造业务任务完成。

当前采集协议为 `business-calibration-export-2`。拟合要求完整、不中断的 40 条开发记录、冻结 checksum 和 synthetic-reference 来源，重建每条请求并检查其自身合法候选、目录、初始状态、指令、模型和全部版本绑定。不同状态下 Choice 候选可以变化，不能用第一条请求的候选验证其他请求。阈值在“已观察的开发分类错误为零”条件下尽量保留覆盖；未观察到合格答案的问题禁用。该条件不是泛化正确率保证。任何验收 case、部分采集、未知 usage 或版本漂移都不能生成有效 profile。v2 将 HTTP 2xx、实际模型绑定完整且 tokens/费用已知的 `invalid_response` 原样计作失败：不将无效答案用于拟合，并把该请求涉及的每个 family 的阈值设为 null，禁用其 Jev 快路线。当前请求没有任何启用 family 时直接进入主模型，不再发送无可用结果的 Jev 请求。40 条收集完成与有效判断覆盖分别报告；不反复重采筛选成功答案。其余服务故障仍停止。旧 v1 保留全部响应有效的要求，旧 partial 文件不改写。模型、插件摘要、workflow/question/policy/dataset 均确切绑定；缺失或漂移时停止使用快路线。

## 固定验收与报告

默认执行完整固定验收；开始前需要已经生成的开发 profile：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business run --live --ledger .decagent/business-eval/global-jev-ledger.json --source-database "$env:DECAGENT_TEST_DATABASE_URL" --profile .decagent/business-eval/profile.json --output .decagent/business-eval/holdout.json
```

`--max-trials N` 可用于受限探测；计划分母仍保留完整 720，未运行 trial 明确列出，不会形成通过结论。每个 trial 后刷新输出文件，预算不足、unknown/pending Jev usage、任务预算暂停或恢复阻塞时保留部分报告并停止。输出路径已存在时拒绝覆盖，使用新路径保存新的运行。

离线复算保存报告：

```powershell
.venv/Scripts/python.exe -m decagent.evaluation.business report --input .decagent/business-eval/holdout.json --output .decagent/business-eval/holdout-recomputed.json
```

每策略统计正确率完整分母、失败状态、确认/澄清、降级、模型 calls、tokens、已知费用、CLI calls、常见机器耗时 p50、累计机器耗时及人工等待。每个 trial 还保留动作状态、真实回执、CLI 命令耗时和实际模型。机器耗时覆盖 worker 中的规划、治理、CLI 和生产结果核实；不计准备初始测试资源及评分器额外 get 的时间。额外评分查询在 CLI 明细中单独标记。确认 actor 的目录/资源刷新仍计机器耗时及 CLI calls。

确认 actor 对三个策略采用相同固定策略：通过真实 BusinessControl 对当前具体动作回复 approve，澄清时停止，不补充参考答案。human_wait_seconds=0 明确表示即时脚本 actor，不是现实人工等待的测量；真实用户耗时需单独研究。

只有真实 live、完整 80 案例三轮、usage 已知且同时满足以下条件才报告 passed：

- hybrid 正确率不低于 main；
- 禁止写入为零；
- 常见案例 hybrid 机器耗时 p50 严格低于 main；
- 混合任务集 hybrid 累计机器耗时不高于 main。

任何离线脚本模型、部分执行、未知必要 usage、预算停止或指标失败均为 not_passed。脚本模型的 PostgreSQL/CLI 测试只证明编排、治理和评分连接成立，不能证明 Jev 优势。当前 CliRunner 的 Windows 环境已测试；独立 Linux 主机部署仍待验收，不能用 Docker 内数据库通过来替代。



## 业务结果评分口径

评分版本`business-outcome-2`允许契约声明为只读的补充查询，目标动作和必需参数仍须按顺序出现；额外或重复成功写入不得跳过，缺失目标读取、错误参数或错误最终业务状态仍失败。澄清可先查询，但任何尝试写入均不符合澄清目标。评分器的最终工单核实结果保存在每条记录的`scorer_verified_ticket`中，额外只读查询的时间和调用量仍完整计入策略耗时。首次39/720的旧部分对照保留为测量缺陷证据，修复后完整重跑另存`holdout-v3.json`，不拼接、不覆盖旧correct值。

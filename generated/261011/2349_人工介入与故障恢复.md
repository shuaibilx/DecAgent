# 人工介入与故障恢复

本页用于处理业务工作台中等待你的任务。字段定义见[API 与规划协议](2349_业务API与规划协议.md)。

## 确认一个业务变更

1. 打开任务，检查“需要你决定”中的命令、全部参数、对象 ID、当前 revision 和状态。
2. 确认目标正确后，选择“批准此操作”。回复后任务自动排队。
3. 查看业务结果、动作回执和有序事件，确认实际结果。

已有工单的改派、解决、关闭、重开和优先级变更都需要具体确认。
首次明确分派、新建、开始处理和评论也要通过插件契约及当前状态检查。

## 修改提案或拒绝

1. 查看“编辑完整参数后重新校验”，保留完整参数 JSON，修改需要改变的字段。
2. 提交修改。新的提案会重新校验并要求确认；编辑本身不执行变更。
3. 确认新提案的全部参数后批准。

参数没有变化时，直接批准或拒绝原提案。无变化的编辑会被拒绝，原审批仍保持待处理。

不希望执行时选择拒绝。任务会停止，原业务资源保持未执行该操作的状态。
模型以后给出的建议不覆盖这次拒绝。

## 补齐缺失事实

1. 阅读具体问题，提供对象的真实 ID、部门、目标或其他必要事实。
2. 对同名人员，使用“部门 + 姓名”或目录中的准确人员 ID。
3. 提交补充。任务重新读取业务上下文并校验下一步操作。

例如目录中有两个张伟，可补充“请分配给 IT Support 的张伟”。
无法确认真实对象时，不从名字猜 ID。

## 处理过期确认

1. 原确认提示资源已变化时，等待任务读取新的 revision 和状态。
2. 检查新提案。旧授权不会自动迁移到新摘要。
3. 仍希望执行时批准新提案；状态已经不允许的操作会停止。

目录新增同名人员或所选人员停用时，即使工单 revision 未变，也会重新判断澄清或拒绝，
不会按旧的允许结果执行。

## 恢复预算暂停

1. 检查已用调用、token、费用和暂停原因。
2. 在“调整预算”中填写明确的调用、token、机器运行秒数和费用上限并保存恢复。
3. 任务从同一持久化 checkpoint 继续，沿用已保存的计划及已完成回执。

新上限仍不足时，任务会继续暂停。不要把未知 usage 当作零来绕过限制。
等待你回复的时间不计入机器运行时间。

## 核实未知写入

1. 任务显示“等待核实执行结果”时，查看 operation ID 和原动作参数。
2. 选择“核实并恢复”。系统查询提交回执，再查询资源历史。
3. 回执和输入摘要、命令、对象 revision 相符后，任务才采用已完成结果。
4. 查不到可信回执时，保持等待并调查插件后台；不要另建相同写入来试探。

超时或响应丢失不等于没有写入。恢复不会盲目重发未知操作。
调用数、token 或费用耗尽仍可核实已发出的操作；机器运行时间耗尽时，先调整时间预算再核实。
图达到 128 步后，仍可显式核实已发出的操作，但不会重新开始规划或新增写入。

## 取消与重启

选择取消后，租约立即撤销。旧 worker 无权保存结果或开始新动作。
已经在插件后台提交的写入可能仍存在，应按原 operation ID 核实实际状态。

服务重启后，待确认问题、原参数和有序历史仍保存在数据库。
已完成动作复用原回执；尚未完成的节点从原 checkpoint 继续。
恢复 execute 节点时先读取持久化动作日志；已经发出的写入先核实原 operation ID。
该写入造成的资源版本变化不会被当作新操作的理由。
创建后再澄清人员时，新的规划上下文仍携带已创建工单、动作 ID 和核实回执。
遇到图版本不兼容时保留 recovering 状态，由维护者按迁移说明处理，不重置任务。

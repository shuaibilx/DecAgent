# 业务任务迁移与恢复

业务能力是 DecAgent 的默认产品方向。旧仓库修复任务仍使用原 repository_repair 路径，原 Waku 代码和运行数据没有迁移。

## 数据变化

只追加迁移，不修改既有 SQL 或 checksum。005 创建业务作用域并增加任务类型：业务任务关联 business_scope_id；修复任务仍必须关联 project_id 和有效提交 SHA。业务事件通过任务外键关联，不伪造仓库。工单迁移另外创建 business schema；备份同时包含 app、checkpoint 与 business。

旧修复 worker 仅领取 repository_repair；业务图的版本独立检查。任务动作、确认、费用记录与 checkpoint 继续使用统一 task ID。

## 升级操作

从 DecAgent 根目录、已安装项目依赖的 Python 环境执行：

```powershell
python -m decagent backup <新的备份目录>
python -m decagent migrate
```

迁移前停止任务写入并保存一致备份。业务数据和凭据不写入源码或聊天。安装包版本、数据库迁移与 worker 必须对应；不能把旧应用直接连接到含新业务任务的数据库。

## 回滚与未知结果

出现不兼容时停止新增任务，保存动作及回执证据，再从备份恢复到新的空数据库和新的证据目录，使用对应应用版本启动。已有业务副作用不因取消或回滚 Agent 而自动撤销。

业务写入结果不明时，先按操作凭据查询，核实成功后关联已有结果。只有业务后端确认尚未发生且支持幂等请求时才允许重试；无法核实的第三方写入交给用户处理。

当前说明描述实现契约，不代表真实实例已完成升级验收；实例升级结果将在本轮验收报告中单独记录。独立 Linux 主机验收仍待办。

## 按类型运行和恢复

业务图使用独立版本 `business-1`，repair 仍保留原图版本。checkpoint 的 thread ID 是任务 ID，
恢复前同时校验任务 ID 与所属图版本。业务 worker 不初始化 GitHub、修复 broker 或仓库工具。
工作台的修复 HTTP/broker 客户端也改为首次使用时初始化。

Windows 原生环境运行业务插件；使用已安装项目依赖的解释器：

```powershell
.venv/Scripts/python.exe -m decagent worker --kind business
```

修复 worker 可独立运行：

```powershell
python -m decagent worker --kind repository_repair
```

Windows 未指定 kind 时串行交替领取两类任务。Linux 未指定 kind 时只领取修复任务，
显式选择 business 会在启动时报告 POSIX 进程限制适配尚未提供，不领取任务后再制造失败。
因此当前 Docker Linux control 的原 worker 不能承担本机业务 CLI。

人工问题先独立 checkpoint，再进入 interrupt；用户在工作台回复后继续同一图。
确认绑定原动作摘要；旧预算恢复事件不能恢复新暂停。
图限制 128 个自主阶段；到达上限后停止新规划和写入，未知结果仍可在明确恢复后只读查询回执。
核实完成后保存证据并以阶段上限结束，不把达到上限的任务包装成成功。

已在专用 PostgreSQL 测试库验证跨新 worker 的确认、未知结果和回执核实，以及原修复 worker 恢复。

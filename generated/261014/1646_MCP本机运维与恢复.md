# MCP 本机运维与恢复

适用当前 Windows + Docker Desktop 实例。日常启动见
[使用指南](1646_MCP业务Agent使用指南.md)。

## 核实服务与配置

```powershell
docker ps --format '{{.Names}}|{{.Status}}|{{.Ports}}'
Invoke-RestMethod http://127.0.0.1:8001/health
Invoke-RestMethod http://127.0.0.1:8000/health
.\.venv\Scripts\python.exe -m ops.local.start plugins list
```

PostgreSQL 保留 55432；MCP 使用 8001；修复 broker 使用 8002。
`DECAGENT_LOCAL_MCP_PORT` 与 `DECAGENT_LOCAL_BROKER_PORT` 不能相同。
`ops.local.start` 将它们转换为可信的 MCP/Broker URL。
模型提案、Skill 文本与工具参数不能替换 endpoint。

本次本机后台进程的日志位于 .decagent/local-control。
启动前已有服务时不要再启动同端口副本。
停止前台服务用 Ctrl+C，按 Worker → API → MCP 的顺序停止。
后台进程停止方法见下节。

## 停止本次后台服务

以下命令只处理 mcp-processes.json 记录且命令行属于当前项目的进程树。
先核对项目根目录；PID 已结束时跳过，PID 被其它进程使用时拒绝操作。

```powershell
$projectRoot = (Get-Location).Path
$processFile = Join-Path $projectRoot '.decagent\local-control\mcp-processes.json'
$processMap = Get-Content -LiteralPath $processFile -Raw | ConvertFrom-Json -AsHashtable
foreach ($roleName in @('business-worker','api','mcp')) {
    $rolePid = [int]$processMap[$roleName]
    $roleProcess = Get-CimInstance Win32_Process -Filter "ProcessId = $rolePid"
    if ($null -eq $roleProcess) { continue }
    if (-not $roleProcess.CommandLine.Contains($projectRoot) -or
        -not $roleProcess.CommandLine.Contains('-m ops.local.start')) {
        throw "进程身份不匹配，拒绝停止 $rolePid"
    }
    taskkill /PID $rolePid /T /F
}
```

强制停止时可能有操作已经提交但响应尚未收到。下次启动后通过原操作核实，
不要因此重新提交业务目标。本轮已实际停止并重启这三个进程验证此流程。
上面的命令不停止 PostgreSQL，也不删除数据卷或凭据。

## 升级与历史任务

追加迁移后，Docker 修复镜像也必须来自同一份源码。
旧 schema 6 镜像会拒绝 schema 11；调整端口不会自动升级镜像。
从项目根目录构建匹配镜像，再启动修复侧组件：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml build migrate worker executor-broker egress-proxy
docker compose -f compose.yaml -f compose.windows.yaml up -d --no-deps egress-proxy executor-broker worker
```

本轮已执行这些命令，修复 broker 在 8002 健康就绪，修复 Worker 正常运行。
它们沿用原数据库与卷，测试验收使用独立容器和数据库。

迁移前备份保存在 .decagent/mcp-migration：

- database-before-mcp.dump：schema 6 数据快照。
- source-before-mcp.zip：切换前源码。
- environment.json：当时版本记录，不包含明文密钥。

本次追加到 schema 11，原工单、历史、回执字段与原 owner 凭据保持一致。
目录初始化、账号初始化和插件登记分别是显式管理步骤。
账号重复初始化保留密码；相同已启用 manifest 重复登记不增加 revision。

旧 business-1 未完成任务标记 business_migration_pending 并暂停；
迁移保留旧 checkpoint、来源及动作记录。
不要手工改 graph_version、employee_id 或清除迁移标记来恢复旧任务。
先审查旧动作与回执，再由员工提交确有必要的新目标。
旧匿名资源保持只读，不能通过新账号“认领”。

## 回滚范围

数据库向前迁移后，旧源码会拒绝新 schema。
回滚要同时恢复旧源码和迁移前数据库到独立位置，
先检查后再切换连接。仅复制旧 Python 文件不能完成数据库回滚。
迁移后新增的员工业务数据不会包含在 schema 6 快照中；
本次已保留全部新数据，没有执行生产回滚。

恢复备份的运维接口是 `decagent restore`，要求目标为新的空数据库与证据目录。
由于当前实例含新数据，本轮未对其执行恢复命令。
备份恢复能力由 PostgreSQL 集成回归验证；人工切换前须另建隔离恢复实例并核对内容。

## 恢复未知业务操作

1. 保留原任务 ID、动作 ID 和 operation_id。
2. 登录原员工，查看“统一操作待办”或任务中的核实状态。
3. 服务仍在写入时等待，再查询原操作。
4. 回执、历史和资源一致时使用原成功结果。
5. 无提交证据且授权仍有效时，由程序沿原 ID 恢复。
6. 证据不一致时保留 unknown，停止自动重试并检查审计记录。

原员工凭据到期时，重新登录并恢复原任务。
预算暂停时提高原任务预算；已提交结果的查询不消耗新的执行许可。
取消或租约变化会阻断旧 Worker 的下一次写入。
